# J. Test Engineering

## 1. 目的

実装工程で単体テスト・結合テスト・カバレッジ確認を標準化し、
「動いたから終わり」ではなく「検証可能な品質工程を通した」状態を
既定にする。

## 2. 標準

- 単体テスト
  - 変更した関数・クラス・分岐を直接検証する。
  - 正常系だけでなく、代表的な異常系と境界値を含める。
- 結合テスト
  - モジュール境界、CLI、設定読み込み、永続化、外部契約の接点を
    代表シナリオで検証する。
- カバレッジ
  - 本repoの既存ゲートは 80% を維持する。導入先は測定対象・基準をそのrepoの設定で定義する。
  - Python の実行例は `pytest --cov=. --cov-report=term-missing --cov-fail-under=80`。
    実際には採用済みのCIコマンドと測定範囲を使い、下流へ一律にコピーしない。

## 3. 実装工程

1. 変更した挙動・影響する境界・回帰リスクから、必要な検証を選ぶ。
2. 既存試験で確認できる部分は再利用し、不足する異常系・境界値・回帰試験を追加する。
3. I/O 契約や CLI の変更は実際の境界を通す。必要なら subprocess や隔離環境の通常installを使う。
4. 期待挙動が明確なら TDD を推奨する。文書修正はlint・参照・内容整合を確認し、文章を写す試験は作らない。
5. 採用済みゲートの coverage、実行コマンド、実結果、未実行・未達の理由を記録する。

## 4. 未達時の扱い

- 採用済みゲートが未達の場合は、そのままマージしない。本repoでは coverage 80% がその基準となる。
- 例外を認める場合は次を必須とする。
  - `docs/acceptance/AC-*.md` に理由を記録
  - PR 本文に対象範囲とフォローアップを記載
  - 次回タスクで解消する Task Seed を起票
