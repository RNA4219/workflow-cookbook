# 長い履歴と記憶更新のドリフト検証

Task: `20260911-04`。owner: RNA4219、実行: Codex。生成前に本仕様とmanifestを凍結する。

## 目的と比較

目的・承認済み案・判断理由・制約・未回答事項・外部操作許可を、長いイベント列と再起動を通して保持できるかを測る。
入力削減率を成功条件にせず、既存の計算補助を全条件に共通適用する。

1. `history`: 原文と全イベント、当該条件自身の過去モデル回答をすべて再提示する。
2. `scripted`: イベントの確定変更を機械的に公開CLIから保存し、agent-taskstateの完全snapshotを復元する。
3. `model`: モデルが直近8イベントから更新操作を生成し、公開CLIに適用する。復元・回答はscriptedと同じ。

主比較はhistory対model。scriptedは書き込みと読み出しの原因を分ける診断条件。
scriptedだけが正しい状態を書けるという仮定を、実運用の記憶抽出能力と混同しない。
modelへの入力にoracleや確定変更の機械可読リストを渡さない。回答を採点前に変更しない。
型・操作名・存在するイベントID・発信者の権限を検証する共通の更新adapterを使う。
ユーザー以外のイベントから承認済み状態を変更する操作を拒否する。未承認のユーザー提案の意味判断はモデルに任せる。
不正操作はそのbatchを適用せず記録し、後続は保存済み状態から続ける。oracleを使って補正しない。

## 長さと事象

新規6合成シナリオを使う。各128イベント、8イベントずつ16更新batch、16イベントごと8回答checkpoint、2反復。
各batchの更新と各checkpointの復元は独立した子プロセスで行い、以前のPythonメモリを使わない。
再起動相当の状態復元であり、実際の停電や数か月の暦日運用を試験したとは主張しない。

確定済み状態は途中の明示変更に追従する必要がある。古い値を固定しても合格しない。
目的変更、採用案変更、判断理由変更、制約追加・解除、質問追加・解消、許可・撤回を含める。
雑多な運用記録、古いメモの再掲、未承認提案、別プロジェクトの決定も混ぜる。
初期状態は各条件に等しく既知として登録する。modelは初期登録後の16batchで抽出更新を実行する。
原文・全イベント・操作・生応答・snapshot・DBを保存する。必須文書とsnapshotを切り捨てない。
1入力262144 bytesを超えたら測定障害とし、黙って削減しない。

## 採点と母数

出力は単独JSON object。従来の11項目にconstraints、resolved_questionsを加える。
文字列・整数・booleanを厳密に区別する。配列は順序不問、重複不可。引用は相対pathと任意の正の行番号。
finish_reason=stopを要求する。余分なキーは採点しない。

主要ドリフト項目はgoal、plan、decision_basis、constraints、pending_questions、resolved_questions、
external_action_allowed、action。1つでも違えばそのcheckpointはドリフトあり。
全8checkpointでドリフトなしの課題割合を主指標とし、最終checkpoint、初回失敗位置、項目別誤りも報告する。
解消済み質問の欠落だけで他の状態保持を覆い隠さないよう、resolved_questionsを除く7項目の保持率も事前指定の副指標にする。
計算や参照文書などを含む全13項目正解率も別に示す。
modelの書き込み後状態を各batchでoracleと照合し、書き込み誤り・読み出し誤り・伝播を分離する。
保存状態の照合は公開question listから解消済みも取得する。モデル入力は標準build_context/assembleをそのまま使う。
準備中に解消済み質問が標準snapshotから除外されることを確認した。この欠落を補足入力で隠さず、復元の限界として測る。
拒否された更新、形式不正、HTTP障害、timeout、未実行を成功扱いしない。

6シナリオ×2反復×3条件×8回答=288回答。model更新は6×2×16=192推論。
負の対照2課題×2反復×3条件×2回答=24回答。総計504モデル要求を予定する。
負の対照は全条件へ同一の固定promptを与え、対応checkpointの正誤一致と全問正解を要求する。
局所的な成功だけで中止したり、失敗だけを再試行したりしない。反復を独立課題として水増ししない。
効果差は6シナリオ単位で集計し、少数合成課題で一般的な優位性を断定しない。
採点器の陽性対照として目的・制約・案・質問・許可を意図的に壊したfixtureを必ず検出させる。

## 実行条件と証跡

同一DGX endpoint・モデルを使い、temperature=0、top_p=1、seed=20260911、thinking=false。
回答上限768tokens、更新操作上限1536tokens。自動再試行0、warmup0、HTTP timeout180秒。
モデル生成を伴わない構造検査とfixture試験を先に実施する。
source・runner・dataset・仕様・モデル設定と順序をhashで凍結し、各比較manifestのpreflight成功後に実行する。
計測障害が3episode連続したら残りは未実行として記録する。意味的誤答では実行を止めない。
実行後は全生出力の独立再採点、hash・件数・usage・対照・モデル前後同一性を監査し、postrunを通す。
GPU共有負荷下の時間は参考値。重み全体のhash、暦日での長期運用、実務全般の無ドリフトは未検証として残す。
結果が悪くても本試験の原本を保存して報告する。本タスクは全問正解になるまでの調整ではなく効果測定である。
production code・旧評価・registry・外部公開先は本実験で変更しない。
